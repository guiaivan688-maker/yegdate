================================================================================
  1. VISION & POSITIONNEMENT
================================================================================

VISION EN UNE PHRASE
  Where To Go YEG est l'agenda intelligent d'Edmonton qui transforme
  « j'sais pas quoi faire » en « voila ma soiree, prete a reserver »,
  en 3 minutes.

POSITIONNEMENT MARKETPLACE
  C'est un marketplace de planification d'experiences a Edmonton, a
  l'intersection de :
    - Airbnb Experiences (catalogue d'activites verifiees)
    - Eventbrite (evenements ponctuels)
    - OpenTable (reservations instantanees)
    - The Knot (planification d'occasions speciales)

  Ce qui nous differencie :
    1. Multi-role natif — couple/famille/amis/affaires/solo en un seul
       site, pas 5 sites separes
    2. Compose sur-mesure — pas que des packages figes, on assemble bloc
       par bloc
    3. Bilingue FR-EN des le jour 1 — rare dans le marche albertain
    4. Hyper-local Edmonton — pas du contenu generique, on parle
       Walterdale, Whyte Ave, Strathcona, Ice District

MISSION
  Aider les Edmontoniens (et les visiteurs) a arreter de scroller Instagram
  et commencer a vivre leur ville, sans la friction logistique
  (reservations, transport, deco, meteo).

PROMESSE CLIENT
    - Tu nous dis budget + humeur + avec qui
    - On te compose une soiree prete a reserver (parfois en 1 clic Stripe,
      parfois en devis 24 h)
    - On gere toute la logistique (permis alcool, deco, photographe,
      plan B meteo, nettoyage)

  4. ARCHITECTURE TECHNIQUE
================================================================================

STACK
    - Framework        : Next.js 16.2.6 (App Router) — « This is NOT the
                         Next.js you know », lire node_modules/next/dist/docs/
                         avant tout changement
    - Runtime          : React 19.2.4 — Server Components par defaut, client
                         islands ciblees
    - Styling          : Tailwind CSS 4 + tokens custom (navy / gold / cream /
                         surface / warm-grey)
    - Animations       : framer-motion 12 (motion.div, AnimatePresence)
    - Icones           : lucide-react 1.16 (heroicons aussi installe, a
                         dedupliquer)
    - Cartes           : leaflet 1.9 + react-leaflet 5 (OSM tiles, ssr:false)
    - Optim images     : sharp (script) + next/image runtime (mozjpeg q=82,
                         max 1920 px)
    - Hebergement      : Vercel (auto-deploy origin/main, edge functions)
    - Base de donnees  : Supabase Postgres 17 (ca-central-1), RLS active
                         partout, region canadienne pour PIPEDA
    - Auth             : Supabase Auth (magic link email + Google OAuth)
    - Paiements        : Stripe Checkout (webhook vers /api/stripe/checkout)
    - Emails           : Resend (quote requests + booking confirmations)
    - Analytics        : composant Analytics custom + Google Search Console
    - Tests E2E        : Playwright 1.60 (chromium-desktop, 4 spec files)
    - i18n             : locale-context custom — useLocale() + t() + toggle
                         FR/EN, dictionnaires JSON

CHOIX ARCHITECTURAUX CLES

  Server Components vs Client Islands
    - Pages segment (couples/famille/amis/business) : SERVER ->
      generateMetadata SEO + JSON-LD inline
    - Pages avec etat (pique-nique, night-out, buffets, carte, reserver,
      admin) : split en page.tsx (server, metadata) + XClient.tsx ("use client")
    - Composants partages : ContextPicker, Navbar, Footer, ActivityCard,
      LoveRooms -> client (useState ou context)

  Stockage des donnees (hybride par design)
    - Donnees quasi-statiques (activites curees, parcs pique-nique, options)
      -> fichiers JSON dans src/data/
    - Donnees dynamiques (offers, bookings, profiles, promo codes, banners,
      reports, partners, composer runs) -> Supabase
    - Migration future prevue : passer les activites/parcs/options en Supabase
      une fois le contenu stabilise pour permettre edition admin live

  Internationalisation
    - 2 locales : fr (par defaut) et en
    - Dictionnaires : src/locales/fr.json + src/locales/en.json
    - Pattern : useLocale() -> { locale, t, toggleLocale }
    - Stored in localStorage + <html lang> reflete
    - Audit voix tu/vous : tout est en tu (tutoiement) coherent

  5. MODELE DE DONNEES
================================================================================

A. DONNEES JSON (statiques)

  activities-{couples|famille|amis|business}.json
  Chaque activite contient : id, slug, segment, title{fr,en}, location,
  address (Edmonton complete), description{fr,en}, longDescription{fr,en},
  image, gallery[], priceRange{fr,en}, priceFrom, priceTo, budgetTier,
  duration{fr,en}, groupSize{fr,en}, ageRange?{fr,en}, season[]
  (spring|summer|fall|winter), mood[] (calme|dynamique|gourmand|decouverte|
  romantique|luxe), tags[], includes{fr[],en[]}, services[] (photographer|
  roomDecor|eventPlanner|picnic), cta (book|quote), rating (4.7-5.0),
  mapsQuery, coords [lat,lng] (pour /carte).

  activities-picnic.json (10 entrees)
    Memes champs, segment varie selon l'occasion.

  picnic-parks.json (23 entrees : 15 outdoor + 8 indoor)
  Chaque parc : id, name, neighbourhood, address, coords, image,
  description{fr,en}, size, capacity, amenities[] (parking, washrooms,
  playground, shelter, lake, heated, accessible...), reservation_required
  (bool | "partial" | "verify"), reservation_note?{fr,en}, best_for[]
  (couple, famille, groupe, event), best_spot{fr,en}, scenic_skyline,
  sunset_view, watchout?{fr,en} (ex : Hawrelak en renovation jusqu'en 2026),
  bbq_allowed, dog_friendly, setting (outdoor|indoor|hybrid), best_season[].

  picnic-options.json (28 entrees)
    20+ add-ons : decoration romantique, panier gourmet, photographe golden
    hour, transport prive, demande en mariage setup (599 $), pack
    anti-moustique, permis alcool, pack soleil, setup hiver, etc.

  Autres
    - buffets.json — restaurants AYCE par categorie
    - weekend-plans.json + plans.json — plans pre-composes
    - guides.json — articles longs SEO
    - edmonton-data.json — events de la ville (calendar municipal)

B. TABLES SUPABASE (dynamiques)
    - profiles          Utilisateurs avec role (client/prestataire/admin)
                        RLS : admin r/w, owner r/w self
    - offers            Offres a reserver via /reserver
                        RLS : admin r/w, public read where status=published
    - booking_requests  Demandes de reservation (Stripe -> confirmation)
                        RLS : admin r/w, owner r/w self
    - composer_runs     Logs des sessions /compositeur (analytics)
                        RLS : admin r/o
    - promo_codes       Codes promo actifs (% off) — RLS : admin r/w
    - site_banners      Bandeau annonce en haut du site
                        RLS : admin r/w, public read active
    - user_reports      Signalements (Report buttons)
                        RLS : admin r/w, owner r
    - partners  [NEW]   Catalogue restos/photographes/fleuristes Edmonton
                        RLS : admin r/w, public read active

  Migrations : supabase/migrations/0001 -> 0011_partners.sql (toutes appliquees)

Important : Ivan opere une entreprise canadienne (Alberta) qui collecte des
donnees personnelles. Stack hebergement choisi pour conformite.

LOIS APPLICABLES
    - PIPEDA (federal) — protection des renseignements personnels
      [OK] Residence des donnees Canada (Supabase ca-central-1)
    - PIPA Alberta — Personal Information Protection Act
      [OK] Hosting au Canada, consentement explicite aux cookies prevu
    - Consumer Protection Act AB — pratiques commerciales
      [OK] Prix transparents, terms et conditions a la racine
    - Anti-Spam (CASL) — emails marketing
      [A FAIRE] Double opt-in newsletter a mettre en place

DECISIONS ARCHITECTURALES LIEES
    - Supabase ca-central-1 (Toronto) -> donnees clients restent au Canada
    - Vercel -> edge global mais data au repo (pas de DB exposee)
    - Stripe -> traite paiements (PCI compliance hors de notre perimetre)
    - Resend -> envoie emails depuis EU, a verifier pour CASL

A FAIRE POUR LA MISE EN CONFORMITE TOTALE
    [ ] Bandeau cookie consent (PIPEDA + Quebec Bill 25 future-proof)
    [ ] Page /confidentialite a etoffer avec sections PIPEDA standard
    [ ] Logger les consents en DB (table consents)
    [ ] Double opt-in newsletter (CASL)
    [ ] Bouton « Supprimer mon compte » (PIPEDA droit a l'oubli)
    [ ] Audit des logs Supabase (logging RGPD-style)
    [ ] Mentionner clairement le hosting Canada dans /about

  Principe directeur : se baser sur sources officielles canadiennes
  (gc.ca, CIRA, OIPC Alberta), PAS des outils tiers.
